fwimg

fwimg

github.com/go-binfmt/fwimg converts an ELF executable into the image a bootloader or ROM loads at a fixed address: a flat binary (objcopy -O binary), a Motorola S-record, Intel HEX or a legacy U-Boot uImage (mkimage, optionally gzip or lz4 compressed), a UF2 file (uf2conv.py) or a Verilog hex memory file (objcopy -O verilog). It is a library and a command, in pure Go, with no binutils, srec_cat or mkimage on the build host.

It moved here from go-coff/peln/fwimg, which is now deprecated; pectl objcopy uses this module.

go install github.com/go-binfmt/fwimg/cmd/fwimg@latest
import "github.com/go-binfmt/fwimg"

elf, _ := os.ReadFile("kernel.elf")
flat, base, err := fwimg.Flatten(bytes.NewReader(elf), int64(len(elf)), fwimg.FlattenOptions{})

Flatten takes the size of the input; SREC, IHEX and UImage return an error.

Try it in your browser

The fwimg playground runs the real command, built for WebAssembly (GOOS=js GOARCH=wasm, v0.8.0), in a Web Worker: pick an ELF, Intel HEX, S-record, uImage, UF2 or Verilog file, choose a format and the options, and download the result. Nothing is uploaded: the page makes no request that carries your file, its Content-Security-Policy allows no other origin, and the input is limited to 32 MiB. The playground produces the same bytes as the native build (a test compares exit code, output and messages on every release); the release also carries a wasip1 build for wazero and wasmtime.

Reading other formats

The input does not have to be an ELF. fwimg recognises an ELF, an Intel HEX file, an S-record file and a uImage by their magic or syntax, so any of them converts to any output; -I forces the format. A raw file is never guessed: it needs -I binary --base ADDR, as objcopy -I binary needs its address.

fwimg -I ihex -O binary -o fw.bin fw.hex
fwimg -I binary --base 0x8000000 -O srec -o fw.srec fw.bin
fwimg info uImage          # the header, as `mkimage -l` prints it

In Go, DecodeIHEX, DecodeSREC, ParseUImage, RawImage and Detect return an Image of sparse segments (with the entry point and the name), which EncodeSREC and EncodeIHEX write back.

The decoders check what the formats define and say where it fails: checksums (with the line number), the end record, the S5/S6 count, both uImage CRCs and the size table of a multi-file image, which is bounded by the header’s size. Overlapping records and data past 4 GiB are refused, not merged or wrapped. They are checked against objcopy -I, srec_cat, mkimage -l and dumpimage in CI, and fuzzed.

objcopy’s options

Since v0.4.0 the options that shape an image are objcopy’s, with the same names, and the S-record and Intel HEX output is byte for byte what objcopy writes (the S0 header text aside), CRLF included with --crlf:

fwimg -O srec -j '.text*' -j .rodata -o fw.srec fw.elf        # keep sections; * and ? match
fwimg -O srec -R '.*' -R '!.text' -o fw.srec fw.elf           # drop sections; ! protects
fwimg -O srec --gap-fill 0xff --pad-to 0x90400 -o fw.srec fw.elf
fwimg -O ihex --change-addresses 0x100 -o fw.hex fw.elf       # --adjust-vma: the same
fwimg -O ihex --set-start 0x80010 -o fw.hex fw.elf            # --change-start N: an increment
fwimg -O srec --srec-addr-len auto --srec-count --crlf -o fw.srec fw.elf
fwimg -O ihex --ihex-mode objcopy --crlf -o fw.hex fw.elf
  • -j and -R select by section name and need an ELF with section headers (read with elfpatch v0.5.0); giving both is refused, as objcopy calls it undefined.
  • --srec-addr-len 16|24|32|auto picks S1/S9, S2/S8 or S3/S7 (auto: the shortest that holds the highest address, as objcopy does); --srec-count adds the S5 (or S6) count record, as srec_cat does.
  • --ihex-mode linear (the default) writes type 04 and type 05 records, as srec_cat; objcopy writes type 02 below 1 MiB and a type 03 start record. An ELF’s entry address is now written to Intel HEX; before v0.4.0 it was dropped.
  • Line endings stay LF unless --crlf is given.

In Go: ELFImage, ELFSections with a SectionSelect, EncodeSRECOpts and EncodeIHEXOpts, and Image.GapFill, PadTo and Offset. The options are compared with objcopy 2.44 and srec_cat 1.64 in CI (the lane fails if a tool is missing).

Safety checks

Since v0.5.0:

  • A gap refusal names the PT_LOAD segments and sections with LMA and VMA and says which of --use-vaddr or -R .data fits; --gap-warn N (default 8) warns when a hole is more than N times the payload.
  • --region NAME=START:SIZE (repeatable, K/M suffixes) refuses a segment that overflows its region or lies outside every region, naming the segment and the byte excess, in ld’s wording.
  • The output is read back and compared byte for byte with what was written, after every write; on a mismatch there is an error and no file. For S-record, Intel HEX and uImage the file is decoded only when the bytes differ, to name the first differing address (start address included). --no-verify turns it off. Non-regular outputs (devices, symlinks) are not read back.
  • SOURCE_DATE_EPOCH sets the uImage time as mkimage does; an invalid value is refused. Unset, the time is 0, where mkimage uses the input’s mtime.

Manifest, info and verify

Since v0.6.0 an image can be described, listed and checked later:

fwimg -O ihex --manifest fw.json -o fw.hex fw.elf   # the image, described
fwimg info fw.hex                                    # any input: format, start, ranges, hashes
fwimg info --json fw.elf                             # the same facts, as a manifest
fwimg verify --manifest fw.json fw.hex               # re-read an image, check every hash
fwimg verify --manifest fw.json -I binary --base 0x8000000 fw.bin
  • The manifest is JSON in a fixed key order: format, base, entry (null without one), pad, size, data_size, the CRC-32 and SHA-256 of the whole image, and for each segment (and each --region) its address, size, source file and both hashes. An ELF input adds its allocated sections, and a uImage output its header fields. The same input and options give the same bytes: there is no timestamp unless SOURCE_DATE_EPOCH is set, and then created is that time in UTC.
  • Addresses are strings ("0x8000000", lowercase hex), because a JSON number cannot hold 64 bits; sizes are integers. The hashes are of the flat image from base, gaps filled with pad, which is what -O binary writes.
  • The schema is manifest-1.schema.json (JSON Schema 2020-12, additionalProperties: false everywhere), also embedded in the library as fwimg.ManifestSchema. A change that is not backward compatible is manifest-2; schema_version says which one a file is.
  • info reads an ELF, Intel HEX, S-record, uImage or (-I binary --base) a raw file. A uImage is listed as mkimage -l does; the others as text or, with --json, as the manifest. Its ranges and start address are compared with srec_info in CI.
  • verify recomputes, from the image in whatever format it is in, the base, size, start address and the hashes of the whole image and of every segment and region, and lists every difference (exit status 1). A manifest written for the S-record checks the flat binary of the same image. data_size is not compared, because a flat binary counts its padding; the start address is compared only if the image has one.
  • The manifest reader is bounded (16 MiB, 65536 entries per list), refuses unknown keys, and is fuzzed.

In Go: NewManifest, ReadManifest, (*Manifest).JSON and Verify, ELFManifestSections and UImageStored.

UF2, Verilog hex and compressed uImage

Since v0.7.0:

fwimg -O uimage --uimage-comp gzip --load 0x80000 --entry 0x80000 -o uImage kernel.elf
fwimg -O uimage --uimage-comp lz4  --load 0x80000 --entry 0x80000 -o uImage kernel.elf
fwimg -O uf2 --uf2-family rp2040 -o fw.uf2 fw.elf        # a family name or a number
fwimg -O verilog --verilog-data-width 4 -o mem.hex fw.elf
fwimg -I uf2 -O binary -o fw.bin fw.uf2
fwimg -I verilog --verilog-data-width 4 -O ihex -o fw.hex mem.hex
  • --uimage-comp none|gzip|lz4 compresses the payload and sets ih_comp (gzip 1, lz4 5); ih_size and the data CRC cover the compressed bytes, as mkimage does. The gzip stream is reproducible (no time, no name, a fixed level). Reading a compressed uImage decompresses it, bounded by --max-size: a decompression bomb is refused, not expanded, and a payload marked gzip that is not gzip is refused (ErrSyntax). info, verify and --json describe the decompressed program; the listing keeps the header as stored.
  • -O uf2 writes uf2conv.py’s layout: blocks of 256 payload bytes, cut where the next segment starts, each padded with zeros. --uf2-family NAME|NUMBER sets the family ID (the table is the one of microsoft/uf2 at a pinned commit; 0 is refused). The reader is strict: magics, block numbers, the block count and the flags are checked, and a file container or a not-main-flash block is refused.
  • -O verilog is objcopy’s $readmemh layout: @ADDRESS lines in uppercase hex, CRLF line ends. --verilog-data-width 1..8 is the word width in bytes, --verilog-endian little|big orders the bytes within a word. Segment addresses must be multiples of the width. The reader accepts // and /* */ comments, @ addresses and _ digit separators, and refuses a token wider than a word.
  • The readers are fuzzed. CI compares the output with mkimage (the compressed header: mkimage -C only tags ih_comp, it does not compress), uf2conv.py and objcopy -O verilog (little-endian output), and the lane fails if a reference tool is missing. The manifest schema lists uf2 and verilog as formats.

In Go: EncodeUF2, DecodeUF2, VerifyUF2, EncodeVerilog, DecodeVerilog, CompressPayload, DecompressPayload, UF2Families and ParseUF2Family.

FIT images

Since v0.9.0, on go-binfmt/fdt:

fwimg -O fit --fit-add fdt:board.dtb --fit-add ramdisk@0x8000000:initrd.img -o kernel.fit kernel.elf
fwimg -O fit --fit-external --fit-align 1000 -o kernel.fit kernel.elf   # like mkimage -E -B 1000
fwimg info kernel.fit                      # as mkimage -l prints it
fwimg verify --require-hash kernel.fit     # every hash node

A FIT (Flattened Image Tree) is a devicetree blob that holds images and configurations. -O fit makes the input the kernel image (architecture and entry from the ELF or --uimage-arch), each --fit-add TYPE[@LOAD]:FILE another image, one hash node per --fit-hash algorithm (crc32, sha1, sha256, sha384, sha512; default sha256), and a configuration conf-1 that names them.

  • Layout. --fit-external keeps the data after the structure (data-offset), --fit-position at an absolute address (data-position), --fit-align is mkimage -B (hex, a power of two). Images are padded to 8 bytes as mkimage -E does with mkimage 2026.10; older mkimage pads to 4, and the differential test then skips those cases.
  • info and verify read a FIT: the listing is mkimage -l’s, compared with it for every image type, and verify checks every hash node without a manifest. A FIT with signature nodes is refused unless --allow-signatures; signatures are not checked, and signing is out of scope.
  • Refusals. External data outside the file, overlapping extents, a position inside the structure, load + size wrapping, a hash node without an algorithm or value, and names that differ only by a unit address are refused. There is a regression test for each FIT CVE of the spec notes (CVE-2018-1000205, CVE-2020-10648, CVE-2021-27097, CVE-2018-3968, CVE-2024-38433, CVE-2021-27138, CVE-2023-39902, CVE-2026-46728), and FuzzFIT runs in CI.

In Go: WriteFIT, AppendFIT, ParseFIT, (*FIT).Verify and (*FIT).Listing. Writing is faster than mkimage -f (1.3x at 1 KiB, 2.7x at 4 MiB, 7.1x at 32 MiB on the CI runner); info is behind mkimage -l (0.7x, 0.4x, 0.1x), an open defect (go-binfmt/fwimg#33).

What it refuses

The input is untrusted, so the module refuses rather than guesses:

  • an image whose size comes from attacker-controlled addresses is bounded before it is allocated (FlattenOptions.MaxSize, a caller-stated limit);
  • a segment that lies outside the input;
  • an address range that wraps;
  • SREC and Intel HEX data that would pass 4 GiB, instead of wrapping;
  • text records that arrive scattered, each separate piece being charged against the same size limit.

The 4 MiB flat row is still behind by about 0.3 ms, a start-up cost of the Go runtime, like the 1 KiB rows, tracked in go-binfmt/fwimg#2. See the README for the method.
